# リレーション

データベースのテーブル同士が、どのような関係になっているかを表す考え方。
代表的なものとして3つ。
- 1体1
- 1対多
- 多対多

## 1対1リレーション

1つのデータに対して、相手側のデータも1つだけ存在する関係のこと。

## 1対多リレーション

一つのテーブルの各レコードが別のテーブルの複数のレコードと関連付けられること。

## 多対多リレーション

例えばこのケース。
1人のユーザーが複数のタグを持てて、1つのタグにも複数のユーザーが存在する場合など。
```
User A
 ├─ Ruby
 ├─ Rails
 └─ Docker
```
```
Ruby
 ├─ User A
 ├─ User B
 └─ User C
```

# アソシエーション

Railsのモデル間の関連性を定義する機能。
アソシエーションを利用することで、異なるモデル同士がどのように結び付いているかを簡潔に表現できる。
主なアソシエーションとして以下3つ。
- `has_one`
- `has_many`
- `belongs_to`

### has_one

`has_one` アソシエーションは、このモデルは相手のモデルを1つ持っているという意味。
例えば、1人のユーザーが1つのプロフィールを持つ場合、Userモデルに対して次のように定義する。

```
has_one :profile
```
これにより、Userモデルのインスタンスから、と書くだけで、そのユーザーに紐づいたプロフィールを取得できる。

### has_many

`has_many` アソシエーションは、1つのモデルが複数の別モデルと関連付けられる場合に使用する。
例えば、1人のユーザーが複数の掲示板を持つ場合、Userモデルに対して次のように定義する。

```
has_many :boards
```

これにより、Userモデルのインスタンスから、そのユーザーが投稿した複数の掲示板情報を簡単に取得できる。

### belongs_to

`belongs_to`は、このBoardは1人のUserに属しているという意味。
例えば、掲示板がユーザーに属する場合、Boardモデルに対してUserモデルを belongs_to :user と定義する。
これにより、Boardモデルのインスタンスから投稿者であるユーザー情報を簡単に取得できます。

```
belongs_to :user
```


### アソシエーションを定義する理由・メリット

アソシエーションを定義することで、簡潔な記述によって関連レコードを呼び出せるようになる。
例えば、Boardモデルのインスタンスから、紐付いているユーザー情報を取得する場合、アソシエーションの有無によって記述方法が異なる。

#### **アソシエーションがない場合**

```ruby
class BoardsController < ApplicationController
  def show
    @board = Board.find(:id)
    @user = User.find(@board.user_id)
  end
end
```

このコードでは、`@board` オブジェクトが持つ `user_id` を取得し、その `user_id` を使ってUsersテーブルから該当するユーザーを検索している。

#### **アソシエーションがある場合**

```ruby
class BoardsController < ApplicationController
  def show
    @board = Board.find(params[:id])
    @user = @board.user
  end
end
```

このコードでは、`@board` オブジェクトが持つ `user` アソシエーションを直接呼び出し、関連するユーザーのレコードを取得している。
アソシエーションが定義されているため、Railsが内部的に適切なSQLクエリを生成し、関連するユーザーのレコードを取得する。
そのほかにも、一方のレコードが削除された際に、関連するもう一方のレコードも自動的に削除するよう設定できるなど、アソシエーションには大きなメリットがある。
そのため、必要なモデル間には適切にアソシエーションを定義することが重要となる。

# **バリデーション**

データがデータベースに保存される前に、そのデータが正しい形式や条件を満たしているかを確認する仕組み。
バリデーションを使用することで、不正なデータがデータベースに保存されることを防ぎ、アプリケーションの信頼性を高めることができる。
代表的なバリデーションとして以下3つ。
- `presence`
-  `length`
-  `uniqueness`

### **presence**

`presence` バリデーションは、指定された属性が空でないことを確認するために使用する。
例えば、ユーザー登録時に名前の入力を必須とする場合、モデルに次のように記述する。
これにより、名前が空の場合は保存に失敗し、エラーメッセージが表示される。

```
validates :name, presence: true
```


### **length**

`length` バリデーションは、指定された属性の長さが特定の条件を満たしているか確認するために使用する。
例えば、パスワードを8文字以上にする場合、モデルに次のように記述する。
これにより、パスワードが8文字未満の場合は保存に失敗する。
```
validates :password, length: { minimum: 8 }
```


### **uniqueness**

`uniqueness` バリデーションは、指定された属性の値が[^3]一意であることを確認するために使用する。
データベースやプログラミングの文脈では、ある属性の値が他のレコードと重複していない状態を指す。
例えば、ユーザー登録時にメールアドレスがすでに登録されていないことを確認する場合、モデルに次のように記述する。
これにより、同じメールアドレスがすでに登録されている場合は保存に失敗し、エラーメッセージが表示される。

```
validates :email, uniqueness: true
```

### dependent: :destroy

親モデルを削除するとその親モデルに紐づく「子モデル」も**一緒に削除できる


### references型

「このデータは、別のテーブルのどのデータと紐付いているのか」を記録するためのもの外部キーを設定するためのメソッド。
このメソッドを使用することで、BoardsテーブルとUsersテーブルを関連付けることができる。
また、`foreign_key: true` オプションを指定することで、外部キー制約を設定している。

外部キー制約とは、あるテーブルのカラムの値が、他のテーブルの特定のカラムの値と一致することを強制するデータベースの仕組み。
この制約を設定することで、データベースの整合性を保ち、不整合なデータの挿入を防ぐ。
例えば、Boards テーブルの user_id カラムに外部キー制約を設定することで、その user_id が必ず Users テーブルの id カラムに存在することを保証する。

```
boards.user_id
```

のように別のテーブルのレコードを指し示すために使用する値のこと。
> 既存のテーブルを参照するので、reference（参照という意味）


## `db:rollback`

マイグレーションを実行した後に、マイグレーションファイルを書き間違えた場合、一度戻して修正できる。

```
docker compose exec web rails db:rollback STEP=1
```

`rollback`は、**すでに適用したマイグレーションを戻す**ことを指す。


## `STEP=1`

`STEP=1`は、**1つ分のマイグレーションを戻す**という意味。


> 学習中ではなく、本番や共同開発では注意しないといけない。すでにチームメンバーや本番環境で適用されている古いマイグレーションファイルを後から書き換えると、環境ごとにDB構造が変わる原因となる。
> そのため実際の共同開発では、新しいマイグレーションを作成　→　そのマイグレーションで変更するという方法を使用することが多いらしい。


## `resources :boards`

`resources :boards`と記述することで、Boardに関する基本的なルーティングアクションをまとめて作成できる。
代表的なActionが以下

- index   一覧
- show    詳細
- new     新規作成フォーム
- create  新規登録
- edit    編集フォーム
- update  更新
- destroy 削除


## only: %i[index]

**Boardのルート全部ではなく、indexだけ作成する**という意味。

```ruby
Rails.application.routes.draw do
  ... 省略 ...
  resources :boards, only: %i[index]
  .. 省略 ...
end
```
これはRubyの記法となる。

`%i[index]`は、`[:index]と同じ意味。


## N+1問題とは

データベースからデータを取得する際、1回のメインの問い合わせ（クエリ）のあとに、取得したデータの数（N件）だけ無駄な追加の問い合わせが実行され、システムの処理速度が大きく低下する現象のこと。

この記事がめちゃくちゃわかりやすい
https://qiita.com/Yuto_Byte/items/2088b195f24e5087bfa4


## N+1問題が発生するケース

まず全てのPostを取得（最初に**1回目のクエリ**）
```ruby
SELECT * FROM posts;
```

取得したPostのuserを1つずつ取得する（**N個の投稿に対してN回のクエリ**）
```ruby
SELECT * FROM users WHERE user_id = 1;
SELECT * FROM users WHERE user_id = 2;
SELECT * FROM users WHERE user_id = 3;
..(以下略)
```
このように「**一つの投稿の中のuser_idを見て、それに合致するuserのレコードを取得**」を全ての投稿で行ってしまう。


## N+1問題に対する対処(includesメソッド)
```ruby
@posts = Post.includes(:user)
```

以上のように取得すると、以下の順序でユーザーのレコードまでまとめて取得してくれる。

### 1. まず全てのpostを取得（1回目のクエリ）
```ruby
SELECT * FROM posts;
```

### 2. postに関連するユーザ情報をまとめて取得（2回目のクエリ！）
```ruby
SELECT * FROM users WHERE users.id IN (1, 2, 3, ...);
```
これで**2回の実行**で全ての投稿とそれに関連するユーザーの情報を全て取得できる。  
IN句でuserのidを括っているので、1回で実行ができている。  
500件でも1000件でも結果的に合計2回の実行で取得してくれる。
