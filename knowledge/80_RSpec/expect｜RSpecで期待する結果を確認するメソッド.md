# expect｜RSpecで期待する結果を確認するメソッド

## 📌 一言でいうと

`expect`は、RSpecのテストで「確認したい値や処理」を指定するメソッド

`to`やマッチャーと組み合わせて、実際の結果が期待どおりかを検証する

**分類：テストコード**  
モデル・コントローラー・ビューそのものに書くのではなく、基本的に`spec`ディレクトリ内のテストファイルに書く

## 📖 仕組み・役割

RSpecは、Rubyのプログラムが期待どおりに動くかを確認するためのテストフレームワーク

基本の書き方は次のとおり

```
expect(確認したい値).to マッチャー
```

例えば、計算結果が`3`になることを確認する場合

```
expect(1 + 2).to eq(3)
```

|部分|役割|この例での意味|
|---|---|---|
|`expect(1 + 2)`|確認する対象を指定する|計算結果の`3`を確認対象にする|
|`.to`|条件を満たすことを検証する|右側の条件に当てはまることを確認する|
|`eq(3)`|判定条件を指定するマッチャー|値が`3`と等しいかを判定する|

マッチャーは、値の一致や状態など、具体的な判定条件を表すもの

`expect`だけで合否が決まるわけではなく、`to`とマッチャーを組み合わせて検証する

```
expect(1 + 2).to eq(3)     # 期待どおりなので成功
expect(1 + 2).to eq(5)     # 期待と異なるので失敗
expect(1 + 2).not_to eq(5) # 5ではないので成功
```

- `to`：条件を満たすことを確認する
- `not_to`：条件を満たさないことを確認する

## 💻 コード例

### 値が一致することを確認する

```ruby
# spec/calculation_spec.rb
RSpec.describe "足し算" do
  it "1と2を足すと3になる" do
    expect(1 + 2).to eq(3)
  end
end
```

`it`は、確認したい動作を一つのテストとして定義するメソッド

その中で`expect`を使い、計算結果が期待した値になっているかを確認する

### モデルのバリデーションを確認する

以下は、`User`モデルに名前の入力を必須にするバリデーションがある場合の例

```ruby
# app/models/user.rb
class User < ApplicationRecord
  validates :name, presence: true
end
```

```ruby
# spec/models/user_spec.rb
require "rails_helper"

RSpec.describe User, type: :model do
  it "名前が空なら無効になる" do
    user = User.new(name: "")

    expect(user).not_to be_valid
  end
end
```

`be_valid`は、対象の`valid?`メソッドを呼び出して判定するマッチャー

この例では、名前が空のユーザーがバリデーションを通らないことを確認する

|コード|分類|役割|
|---|---|---|
|`validates :name, presence: true`|モデル|名前を必須にするルールを設定する|
|`expect(user).not_to be_valid`|モデルのテスト|そのルールに沿って無効になるかを確認する|

### 処理による変化を確認する

```ruby
RSpec.describe "配列への追加" do
  it "要素が1つ増える" do
    numbers = [1, 2]

    expect { numbers << 3 }
      .to change { numbers.length }.by(1)
  end
end
```

`expect { ... }`には、実行する処理をブロックとして渡す

`change`は処理の前後で値がどう変わったかを確認するマッチャー

この例では、配列への追加処理によって要素数が`1`増えることを確認する


## 🎯 使用場面

- 計算結果やメソッドの戻り値が正しいかを確認するとき
- モデルのバリデーションが期待どおりに働くかを確認するとき
- データの保存によってレコード数が増えるかを確認するとき
- リクエストに対するレスポンスが期待どおりかを確認するとき
- 画面に必要な文字や要素が表示されるかを確認するとき

確認する対象に応じて、モデルスペック・リクエストスペック・システムスペックなどで使用する

## ⚠️ 注意点・よくある間違い

### `expect`はRubyの標準メソッドではない

ここで扱う`expect`はRSpecが提供するメソッド

通常のRubyコードで、RSpecの準備なしにそのまま使えるものではない

### バリデーションを設定するメソッドではない

`validates`はモデルにルールを設定するもの

`expect`は、そのルールや処理が期待どおりに動くかをテストで確認するもの

### 値の確認と処理の確認で書き方が異なる

```ruby
# 値を確認する場合
expect(1 + 2).to eq(3)

# 処理の前後で変化を確認する場合
numbers = [1, 2]

expect { numbers << 3 }
  .to change { numbers.length }.by(1)
```

`expect(...)`では、引数の式を評価した結果を渡す

`expect { ... }`では、処理をブロックとして渡し、マッチャーが必要なタイミングで実行できるようにする

### `be_valid`は保存成功を確認するものではない

`be_valid`が確認するのは、`valid?`の結果

バリデーションを通ることと、データベースへの保存が成功することは区別する

## 💡 自分がつまずいたところ

- `expect`が確認対象を指定し、マッチャーが判定条件を指定するという役割の違い
- `to`と`not_to`で、期待する条件が反対になること
- モデルのルールを書く場所と、そのルールをテストする場所の違い
- `expect(...)`で値を渡す場合と、`expect { ... }`で処理を渡す場合の違い
- `be_valid`による確認では、データベースへの保存は行われないこと

## 🔄 復習メモ

### Q1. `expect`は何をするメソッド？

RSpecで確認したい値や処理を指定するメソッド

`to`やマッチャーと組み合わせて、期待どおりかを検証する

### Q2. `expect`はどこに書く？

基本的に`spec`ディレクトリ内のテストファイルに書く

モデルを確認する場合は、`spec/models/user_spec.rb`などに書く

### Q3. マッチャーとは何？

「値が等しい」「有効な状態である」など、具体的な判定条件を表すもの

例えば`eq(3)`は、値が`3`と等しいことを確認するマッチャー

### Q4. `to`と`not_to`の違いは？

`to`は条件を満たすこと、`not_to`は条件を満たさないことを確認する

### Q5. `expect(user).to be_valid`は何を確認する？

`user.valid?`を呼び出し、ユーザーがバリデーションを通ることを確認する

保存できたことを確認するコードではない

### Q6. `expect(...)`と`expect { ... }`の違いは？

`expect(...)`は確認したい値を渡す書き方

`expect { ... }`は実行する処理を渡す書き方

処理による値の変化や、例外の発生などを確認するときにブロックを使う
