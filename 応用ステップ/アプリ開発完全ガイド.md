**「アプリをどう作るか」ではなく「どんな姿勢でアプリ開発に向き合うか」**

エンジニアにとってアプリは単なる「成果物」ではなく、**自分の能力・考え方・姿勢を可視化するツール**
**意図・工夫・改善の痕跡** が重要

大切なこと
## 技術力
- どの言語・フレームワークを選んだか
- 設計や実装のクオリティ
- エラーや課題への対応方法
>GitHub上のコードや履歴で一目でわかる

## 思考力
- なぜその機能を作ったのか
- ユーザー体験をどう設計したのか
- どうやって機能に落とし込んだのか
- 制約やトレードオフをどう考えたか
> READMEやIssue、PRのコメントで表現できる

## 課題発見力
- 「どんな課題を解決したいのか」を具体的に言語化できるか
- ユーザーが本当に困っていることをどう見つけたか
>アプリの機能・UI・UX設計から伝わる

## 継続力・姿勢
- コミットの粒度や頻度、改善の痕跡
- 課題やレビューを受けて改善する姿勢
>GitHubの履歴や改善サイクルで見える


# 開発における心得（超重要）
## 心得①：個人開発＝自分の近くの課題を解決する
- 今の自分
- 身近な人
>**「解像度が高い課題」だけが武器になる= 自分だけにしか作れないアプリ**

## 心得②：ユーザーあってこそのサービス
- ユーザーが誰かを意識して作ることが大事
- 自分だけではなく、**明確なターゲットユーザーを想定し、体験を考える**
- 最初は自分もユーザーになれるが、最終的には他者にも使える設計を目指す
- **フィードバックを受け改善する姿勢も重要**

## 心得③：「最低限の計画」を持って、作りながら考える
**※「作りながら考える」とは、計画なしに作ることではありません。**

次のような進め方はNGです。

- ゴールやユーザーを決めずにコードを書き始める
- 思いついた機能をその場で追加していく
- READMEやIssueを後回しにする

ここで言う「作りながら考える」とは、  
**最初に最低限の計画を立て、その計画を作りながら更新していくこと**を指します。

- 最初から完璧な設計は不要
- 重要なのは **「何をどう考えたか」「どの手順で進めたか」がわかること**
    - README / Issue / PR / コメントなどで手順や判断理由を明示
- **AIや他人に丸投げせず、自分の言葉で課題・工夫・選択を記録する**
- 後から改善や拡張をする際も、**手順が可視化されているとスムーズ**





## 本リリースまでのチェックリスト

最後に、本リリースまでに確認すべき項目をまとめます。**すべてを完璧にする必要はありませんが、1つでも多く取り組むことで、ポートフォリオの質が大きく変わります。**

### 機能・設計

- [ ] CRUDだけでなく、ユーザーの課題を解決するコア機能がある
- [ ] 「入れなかった機能」とその理由を記録している
- [ ] ユーザーからフィードバックをもらい、改善に活かしている

### コード品質

- [ ] テストファイルが6件以上ある（モデル・リクエスト・結合テスト）
- [ ] テストヘルパー（テストデータ作成ツール等）を使っている
- [ ] カバレッジツールを導入している
- [ ] N+1問題を検出・解消している
- [ ] 複数の処理がセットになる箇所にトランザクションを使っている
- [ ] ロジックが適切なレイヤーに分離されている（Service層・カスタムフック等）
- [ ] 権限管理を実装している

### 開発環境・運用

- [ ] Linter / Formatterを導入し、ルールをカスタマイズしている
- [ ] GitHub ActionsでCIを設定している（テスト・Lint自動実行）
- [ ] エラー監視ツール（Sentry等）を導入している
- [ ] `.env.example` を用意し、秘密情報をコードに含めていない

### README

- [ ] 自分の実体験に基づく課題発見が書かれている
- [ ] 差別化が「機能の有無」ではなく「体験価値」として書かれている
- [ ] 技術選定の比較検討が書かれている
- [ ] ER図と設計意図が掲載されている

### GitHub運用

- [ ] Issueに見積もり（ストーリーポイント）をつけている
- [ ] PRにはタイトルだけでなく、背景・理由をbodyに書いている
- [ ] PRとIssueを紐づけている（`Closes #123` 等）
- [ ] コミットメッセージにプレフィックスをつけている（`feat:` `fix:` 等）
